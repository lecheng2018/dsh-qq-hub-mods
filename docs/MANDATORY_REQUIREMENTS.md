# 硬性要求与合并门禁

适用仓库：`lecheng2018/dsh-qq-hub-mods`。核对日期：2026-11-20；基准提交：`3c2fadd2b0e2cd9743e4138f551530b763b99d6b`。

本文是拟随本次文档合并采纳的强制贡献规则。**必须 / 禁止** 表示不满足时不得合并或发布；**应当** 表示有合理替代时可以在 PR 解释；**可以** 表示可选。现有代码检查、宿主规范和本次新增评审要求分别列明；本文不会自行改变 CI、GitHub 分支保护或宿主实现。

## 1. 执行边界

规则适用于新模块，以及已有模块本次改动涉及的行为和交付文件。不能因为历史代码存在类似写法，就对新增风险放行；也不因新增文档而覆盖已发布包或批量改变历史模块版本。

- **自动**：本仓脚本或工作流已有对应检查，但仍受 [开发基准](DEVELOPMENT_BASELINE.md) 所列限制约束。
- **评审**：本次制定、需要作者提交证据和维护者人工核验的门禁，目前没有同等自动化保证。
- **宿主**：MODULE_SPEC 描述的宿主约束；必须针对目标宿主验证，不能仅由本仓模块调用证明。

每条规则的编号可用于 PR 评审。触发阻断后须修复，或按第 5 节登记受控例外；密钥泄露、越权、跨会话泄露、绕过消息台账、篡改已发布内容不得用普通例外放行。

## 2. 模块和接口

| 编号 | 必须满足的要求 | 核验与证据 | 当前执行位置 |
| --- | --- | --- | --- |
| MOD-01 | 发布模块位于 `modules/<id>/`；目录名和 `module.json.id` 一致，清单合法，入口、README、LICENSE 齐全 | `node scripts/check.mjs`，并检查入口真实存在 | 自动 + 评审 |
| MOD-02 | 入口采用默认导出的模块定义，id 与清单一致，`setup` 为函数；版本与清单同步 | 对照 MODULE_SPEC 和入口；目标宿主安装/加载验证 | 宿主 + 评审；本仓 check 不等同于入口加载器 |
| MOD-03 | 新模块只使用 Node 内置模块作为运行时依赖；不能依赖开发机私有路径或未交代的外部程序 | 审查 imports、子进程和资源引用；记录外部前置条件 | 评审 |
| MOD-04 | `capabilities` 如实声明使用的能力；不得将声明当作权限检查或隔离证明 | 对照网络、存储、调度、工具、面板等实际调用 | 清单类型部分自动；语义评审 |
| API-01 | 工具按宿主支持的 `api.tool` / `defineTool` 契约注册，参数在执行侧校验；涉及权限的操作在执行时再次鉴权 | 合法/非法参数、开关变化、权限不足回归测试 | 宿主 + 评审 |
| API-02 | 变更已有工具、配置、钩子、面板动作或返回含义时，写明兼容性；不兼容变更提供迁移说明并按主版本处理 | API/模块 README 同步，消费者回归用例 | 评审 |
| API-03 | 不编造宿主 HTTP 路由、错误码或 SDK 保证；观察到的模块用法与稳定宿主契约必须区分 | 源码路径、目标宿主版本/提交、调用与返回证据 | 评审 |
| API-04 | 面板动作的方法、路径和参数与后端注册一致；状态读取不得意外触发发送或配置写入；后端独立鉴权 | 面板操作记录和动作单测，敏感返回脱敏 | 评审 + 宿主 |

## 3. 安全、数据和运行行为

| 编号 | 必须满足的要求 | 核验与证据 | 当前执行位置 |
| --- | --- | --- | --- |
| SEC-01 | 所有用户消息必须进入宿主 Outbox；禁止绕过台账直接调用发送协议 | 正常/失败/重试时的台账记录，源码发送路径 | MODULE_SPEC 宿主要求 + 评审；原始 OneBot 桥接须专项验证 |
| SEC-02 | 记忆和私有数据按会话隔离；私聊互不可见，群聊不可读私聊；无 scope 历史记录默认不可见，身份或 scope 无法确定时拒绝访问 | 至少两私聊一群聊的隔离用例，旧数据缺 scope 用例 | MODULE_SPEC 宿主要求 + 评审 |
| SEC-03 | 模块数据仅写自己的宿主分配目录；禁止路径穿越、逃逸、跨模块读写或依赖宿主私有目录布局 | 非法路径、符号链接/边界处理（适用时）、数据目录用法审查 | 评审 + 宿主；本仓 check 未证明全面执行此规则 |
| SEC-04 | 密钥走 `password` 类字段；源码、fixture、日志、普通配置回显和错误中不得含有效凭证 | 脱敏回归、变更与日志审查；密码字段空值语义按目标宿主核验 | MODULE_SPEC 宿主要求 + 评审；目前未配置专门 secret scan |
| SEC-05 | 用户输入、外部页面和模型输出不得直接成为 shell 命令、代码或未经校验的文件路径；不得关闭 TLS 校验 | 输入验证用例；`exec`、`eval`、动态加载与文件写入审查 | 评审 |
| SEC-06 | 可配置 URL 和跳转必须有适用的协议/目标约束；浏览器和登录模块不得把任意来源升级为宿主权限 | 明确允许访问的目标和必要限制；本地/私网访问有明确业务依据与授权边界 | 评审，不声称已有全局 SSRF 防护 |
| RUN-01 | 外部网络调用有有限超时、有限重试、响应大小或条数边界；重试不能形成无限循环或无限消息重复发送 | mock 超时/失败/超大结果；记录各模块实际预算 | 评审；不虚构统一毫秒阈值 |
| RUN-02 | 定时任务、监听器、浏览器和长连接按宿主支持的清理机制释放；重复启停不重复运行 | setup/停用/重启回归，部分初始化失败清理 | 评审 + 宿主 |
| RUN-03 | 写数据、发消息、付费调用等副作用要有明确触发条件；重复事件和失败重试不得造成不可控重复 | 重复触发测试、去重/幂等说明及适用边界 | 评审 |
| RUN-04 | 注入内容满足宿主契约；MODULE_SPEC 指定的 `inject` 接口只传纯字符串数组，不把其他钩子自动视为同一接口 | 对应宿主定义和正反例 | 宿主 + 评审 |

`api.dataDir()` 在部分存量模块出现，现有规范又提及无参调用静态拦截；`api.onebot` 也被模块使用。它们属于需要对照宿主澄清的差异，不是许可新增同类写法的先例。源证据见 [接口参考](API_REFERENCE.md) 的待核验项。

## 5. 阻断、例外与责任

作者负责提供证据；维护者负责审查契约、安全边界和发布影响。至少一名非作者维护者复核是本次建议采纳的协作要求，尚未证明已配置 GitHub 强制审核。涉及敏感凭证或漏洞细节时，不在公开 PR 中展示秘密。

可例外的工程规则若确有无法立即满足的历史限制，PR 必须登记：规则编号、受影响范围、原因、替代控制、负责人、到期日期及跟踪任务；维护者在 PR 明确批准，过期后重新审查。不得无限期写“后续补充”。CI 技术失败不能仅靠删除测试、改为空断言、关闭检查或虚构通过记录来处理。

发布后出现安全问题时：停止继续发布受影响版本，按现有撤回清单登记，修复后使用新版本；如有凭证泄漏先轮换；保留脱敏复盘记录。删除源码不能撤回客户端已经下载的包。

## 6. 仍需实现的自动化

下列事项属于后续工程工作，本次文档不宣称已完成：

- Git 缺失、tag/diff 失败时让版本检查 fail-closed，并覆盖删除模块与工作区验证场景。
- 把工具、面板和 SDK 的稳定契约形成可执行的宿主联调测试。
- 明确测试零发现、条件 skip 和归档测试的处理策略；为目标范围增加覆盖率测量后再约定阈值。
- 配置密钥检测、必要的权限/路径/网络安全测试和产物内容检查。
- 将需要的 CI 状态与人工审核绑定 GitHub 分支保护，并确保 release 仅接受满足门禁的提交。
- 测量网络、调度、内存和包大小基线后设置可重复验证的性能预算；目前没有可据实报告的统一性能阈值。
